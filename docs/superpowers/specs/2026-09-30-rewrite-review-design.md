# 改写审阅设计（讨论稿）

## 目标

平台是通用的：不管轨迹来自哪种 harness（基于 Claude Code、Codex 或 pi，再加 MCP、Skills、Instructions、Hooks），也不管改写流水线怎么实现，都能在平台上审阅"原始轨迹 → 改写后轨迹"。它服务三件事：

1. **抽检改写质量**：逐处判定改动对不对，按错误类型、类别、方案条目统计，找改写流水线的问题。
2. **找漏改**：改写后的轨迹里，仍在调用、读取或提到已删除 harness 组件的地方（规则层）。
3. **把关入训**：规则把每条样本分成可进 / 待看 / 不进，人只看待看的；导出可进的 JSONL 和要重跑的样本清单。

单人使用。判定只在平台内用。

## 核心原则：平台算的 vs 流水线给的

| 平台自己算（任何改写都有） | 流水线可选附带（有才显示） |
| --- | --- |
| 原始与改写后样本按样本 id 配对 | 每处改动的类别、理由、引用的方案条目、证据、校验警告 |
| 步骤对齐：保留、改动、删除、合并、新增 | 定位提示：哪个定位器因为什么选中了这条消息 |
| 词级 diff：思考、正文、工具参数和返回 | 审阅过但保留原文的片段 |
| 工具调用的增删改、系统提示按段落比较、工具声明比较 | 样本状态（改写完成 / 阻塞 / 失败）和原因 |
| harness 增减：按四层清单比较两边，得出删掉 / 新增 / 保留的组件 | 消息下标映射（有它对齐更准） |
| 残留：改写后仍在用已删除组件的步骤 | 改写方案条目表（方案里每一条的原文、去向、新文） |
| 摘要同步：压缩摘要的上下游在改写后是否仍一致 | 流水线自己的摘要同步记录 |

没有任何注解时，改写审阅照样能用：diff、结构变化、harness 增减、残留、判定、分流都来自平台。有注解时，改动旁边多出理由等信息。

## 数据

### 改写批次

一个批次 = 原始集合 + 改写后集合 + 可选的注解来源。两个集合都是普通的平台集合，用现有的适配器导入，格式不限。记录按样本 id（`run_id`）配对。只在一边有的样本单独列出。

### 注解适配器

注解通过适配器读入，统一转成下面的内部结构。第一版有两个适配器：

1. **中性注解 JSONL**：平台定义的格式，任何流水线都可以直接输出（见附录）。
2. **改写运行目录**：`run_config.json` + `rewritten.jsonl` + `chains/*/results.jsonl` + `chains/*/status.json` 这种布局，也就是同事现在的流水线产物。条款表按 `run_config.spec.clauses` 在 `../../spec/` 下找，转成方案条目。

以后新的流水线要么直接输出中性格式，要么加一个适配器，改写审阅本身不用改。

### 对齐

平台对每对样本做步骤对齐。

- **有消息下标映射时**：改写后第 j 条源消息对应原始第 `index_map[j]` 条，直接映射，用于验证和精确对齐。
- **没有映射时**，按下面的顺序推断：
  1. 工具调用 id 相同的步骤先对上（改写通常保留调用 id）；
  2. 系统提示对系统提示；
  3. 锚点之间按角色和文本相似度对齐；
  4. 原始里没对上的模型步骤，如果它的文字大部分出现在下一个对上的改写步骤里，算合并进去，否则算删除；
  5. 改写后没对上的步骤算新增。
- **验证**：用带 `index_map` 的真实运行检查推断结果和映射是否一致。

**合并步骤**的 diff 基准是被合并各步原文的拼接（非空的部分用空行相连）。工具调用按 id 比较：原始有、改写后没有的算删除；参数或返回变了的算修改。

### 存储（SQLite，和现有索引同库）

| 表 | 内容 |
| --- | --- |
| `rewrite_batches` | 名字、原始集合、改写集合、注解来源（适配器、路径、元信息）、方案条目、创建时间 |
| `rewrite_annotations` | 批次、样本 id、注解（改动、目标消息、状态、下标映射、同步记录） |
| `rewrite_verdicts` | 批次、样本 id、对象键（改动 / 漏改 / 残留 / 整条记录）、判定、错误类型、备注、时间 |

diff、对齐、残留和分流都按需计算，不落库，内存里缓存。

## 界面

侧栏导航加"改写审阅"，取代现在"对比"页里的"改写对比"入口。

### 设计原则

1. **一栏读，右侧详情栏。** 读的是改写后的轨迹，正文宽度保持可读；不按版本分栏。
2. **正文只有三种标记**：红色删除线（删掉的字）、绿色底（新增的字）、琥珀色虚线（残留）。类别、理由、方案条目、警告只出现在详情栏里。
3. **默认折叠**：没改的连续步骤折成一行；改了的步骤只显示改动附近的文字，可展开全文。
4. **结构变化单独画**：删掉的调用、合并、改了参数的调用画成灰色事件条，不和文字 diff 混在一起。
5. **键盘优先**：跳转、判定、切换视图都不用鼠标；判定进度常驻顶部。

### 批次列表 `#/rewrites`

- 已有批次列表。
- 新建批次：选原始集合、改写后集合，可选填注解路径。
- 批次的记录表：样本、段、状态、改动数、残留、分流结果，点进单条记录。

批次总览（漏斗、分布、分流设置、导出）和改动队列在单条记录页确认以后再做。

### 单条记录 `#/rewrites/<批次>/r/<样本 id>`

**顶部**
- 迷你地图（复用步骤条），标出改动、删除、合并、残留和判定状态，点哪跳哪；
- 同一 episode 的段切换；
- 本记录的判定进度和分流结果。

**主栏：改写后的轨迹**
- **第一张卡"harness 增减"**：
  - 组件按四层列出删掉 / 新增 / 保留；
  - 系统提示按一级标题列出删、改、留；
  - 工具声明列出增删和重新定义的；
  - 另用灰色列出"改写后仍超出原生 agent 的组件"，只作提示，不算残留。
- **每一步**：内联词级 diff。没改的连续步骤折成"· · · 12 步未改（展开）· · ·"。
- **结构事件条（灰色）**：
  - 删除的调用（可展开看原调用和返回）；
  - 合并（"合并自原 #35 #37"）；
  - 参数或返回改了的调用（展开看 diff）；
  - 删除的步骤。
- **摘要同步**：压缩摘要的上下游标"⇄ 与下一段同步 ✓ / ✗"。
- **残留**：文字上用琥珀色虚线标出，步头标"残留"。

**右侧详情栏**
- **选中一处改动时**：
  - 位置和字段；
  - 有注解时依次显示：类别、理由、方案条目（原文 → 去向 → 新文）、证据、定位提示、校验警告；
  - 没有注解时写明"流水线没有记录这处改动"；
  - 判定按钮。
- **没选中时**：
  - 本记录的状态和分流原因；
  - 残留列表，逐条"确认漏改 / 忽略"；
  - "标为可进 / 不进"。

**其他操作**
- **漏改标注**：在主栏选中一段文字，浮出"标为漏改"并选类型。
- **训练视角**（`t`）：隐藏 diff 和事件条，只显示改写后的正文，保留残留虚线。
- **键盘**：
  - `j`/`k` 上一处 / 下一处改动；
  - `1`/`2`/`3` 对 / 错 / 待定；
  - `t` 训练视角；
  - `o` 当前步左右并排（原文 | 改写）；
  - `e` 展开全部。

## 错误类型（固定标签）

改动判错时选一个：

1. **语义丢失**：删了不该删的信息，比如备选项、否定、数字、计划状态、置信度。
2. **新编内容**：加了原文没有的理由、评价、事实或完成状态。
3. **归因残留**：改完仍指向已删除的 harness 内容。
4. **改过头**：原文有合法出处（用户、新 harness、之前读到的内容），不该改。
5. **不通顺**：语句不通，或和前后文对不上。
6. **其他**：必须写备注。

漏改的类型：文字里的归因残留、工具参数里的依赖、其他。

## 规则层残留

- **定义**：原始 harness 清单里有、改写后 harness 清单里没有的组件，在改写后轨迹的训练步骤里仍被调用、读取、提到或使用其产出。按 `harness.trace` 的四种用法分类，工具参数里的依赖也算。
- **和现有 `rewrite_pairs` 的区别**：现在的做法把两边清单合并后再查，会把改写后合法保留的组件也算成残留；这里只查"原始有、改写后没有"的组件。
- **顺带修一个问题**：`STOCK_SECTIONS` 补上 Claude Code 自带的 "Text output (does not apply to tool calls)" 段。

## 入训分流

规则按顺序判断，先命中的生效：

- **不进**：
  - 注解里样本状态不是改写完成；
  - 有判错的改动；
  - 有确认的漏改或残留；
  - 人工标了"不进"。
- **待看**：
  - 有未处理的残留；
  - 摘要同步检查失败；
  - 注解里带了指定类型的警告、但还没判定的改动。默认指定 `drops_negation` 和 `adds_status_words`，警告类型从数据里读，不写死。
- **可进**：其余记录，以及人工标了"可进"的记录。

## 安全

- 只读源文件和注解目录，不写回。
- 仓库里不放真实数据、内部路径和主机名；测试用合成样例。

## 实现顺序

1. **后端**：
   - 注解适配器（中性 JSONL、改写运行目录）；
   - 批次和判定存储；
   - 对齐、词级 diff、harness 增减、残留、摘要同步、分流；
   - 接口和 CLI。
2. **前端**：批次列表和单条记录页。先在 niulai 上用真实的 pilot 运行看效果，你确认后再做批次总览和改动队列。

## 验证

- **单元测试**（合成样例）：
  - 词级 diff；
  - 有映射和无映射两种对齐，包括合并、删除调用、新增步骤；
  - 注解挂到 diff 上；
  - harness 增减和残留；
  - 摘要同步；
  - 分流；
  - 判定存取；
  - 中性格式和运行目录两个适配器。
- **真实数据**：
  - 导入 pilot 的 skills 运行；
  - 无映射推断的对齐结果要和 `index_map` 一致；
  - 改动数要和它的 `report.json` 一致；
  - 抽查一条有合并的样本。
- **浏览器走查**：单条记录页的折叠、详情栏、判定、训练视角、并排、漏改标注和键盘操作。

## 附录：中性注解 JSONL

每行一个 JSON 对象。所有字段都可选，只有 `sample_id` 必填：

```json
{"sample_id": "task-7_attempt_01",
 "status": "rewritten", "reason": null,
 "index_map": [0, 1, 2, 5, 6],
 "changes": [
   {"message": 4, "field": "thinking", "old": "Per the harness rules I", "new": "I",
    "category": "attribution", "reason": "the rule no longer exists in the target harness",
    "refs": ["plan-12"], "warnings": ["drops_negation: not"],
    "evidence": [{"quote": "…", "source": "user", "verified": true}], "target": "4/rewrite"}],
 "targets": [
   {"message": 4, "task": "rewrite",
    "locator": [{"source": "jev", "score": 0.93, "quote": "…", "reason": "…"}],
    "kept": [{"quote": "…", "reason": "stated by the user"}]}],
 "sync": [{"to": "task-7_attempt_01_context_02", "ok": true, "detail": "exact"}]}
```

另外可以有一行方案条目：

```json
{"plan": [{"id": "plan-12", "group": "Rules", "fate": "removed", "before": "…", "after": null, "note": "…"}],
 "fates": {"removed": "no longer in the target harness"}}
```

- `message`：改写后样本里的源消息下标，从 0 开始。
- `field`：`thinking`（推理）或 `text`（正文）。
- `old` 必须能在原文里找到；`new` 必须能在改写后的文本里找到。
